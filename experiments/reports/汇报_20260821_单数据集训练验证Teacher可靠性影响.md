# MV-OPSD 单数据集训练实验汇报

> **实验编号**：`20260821_mvopsd_single_source`  
> **实验时间**：2026-08-21 16:35—23:40（UTC+8）  
> **运行资源**：node-A / node-B，各 8×H20  
> **实验状态**：两条 Round-1 训练均由用户决定提前终止；另外两条计划 arm 未启动  
> **主要产物**：训练日志、逐步 rollout、全量 VSI-Bench 验证输出、step 25 间隔 checkpoint

## 摘要

本轮实验旨在回答一个明确问题：**MV-OPSD 的效果是否主要由 Teacher 在不同数据源上的可靠性决定？**
此前混合训练池中，各数据源的 Teacher 正确率差异很大，从 `llava_hound_64k` 的 57.7%
到 `spar_32view` 的 19.9%。混合训练只能看到这些监督信号的加权结果，无法判断哪类数据真正有效。
因此，本轮改为一次只使用一个数据集，并优先并行测试：

- node-A：`llava_hound_64k`，Teacher 可靠性 57.7%；
- node-B：`vlm3r_scannet`，Teacher 可靠性 44.0%。

结果表明，两条独立数据源均在训练早期出现相同的**响应长度失控（response-length explosion）**：
模型从直接作答迅速转为逐帧、列表式长篇分析，绝大多数 VSI-Bench 输出在 1,024 token
上限处被截断。`llava_hound` 在 step 25 时 VSI-Bench 由 53.38% 降至 21.92%，
验证输出截断率达到 97.4%；`vlm3r` 在 step 25 时由 53.36% 降至 18.98%，
截断率达到 100%。之后继续训练至 step 175 / 100，分数仍停留在约 21% / 20%，未恢复。

与此同时，VOPD loss 持续下降。这说明优化器成功降低了 Student 与 Teacher 的 token-level
分布差异，但这种分布对齐没有保持任务能力与简洁作答格式。换言之，**蒸馏目标正在收敛，
而下游能力正在退化**。

本轮可以确定的直接失效机制是：**整段 response 的生成风格被推向长推理，
继而在固定预算下被截断，最终答案无法稳定输出**。当前配置中 Teacher 开启 thinking，
Student 与评测关闭 thinking；Teacher 虽然不生成回答，但会在开放的 `<think>` 上下文中，
对 Student 的整段 response 做 teacher forcing。这一语义不对称是最值得优先验证的机制假设，
但本轮没有 `teacher thinking on/off` 单变量对照，因此不能把它写成已经证明的唯一根因。

## 一、实验目的与研究假设



### 1.1 背景

Teacher 可靠性全量评测显示，不同训练源的监督质量差异显著：


| 数据源               | Teacher 可靠性 | 备注                     |
| ----------------- | ----------- | ---------------------- |
| `llava_hound_64k` | 57.7%       | 开放式视频描述，语义 judge 口径    |
| `vsi_appr_order`  | 55.3%       | 选择题，与 VSI-Bench 部分题型同源 |
| `vlm3r_scannet`   | 44.0%       | 选择题与数值题，规则评分较稳定        |
| `spar_32view`     | 19.9%       | 部分空间想象题受回答完整性影响        |


此前使用混合池训练时，高质量与低质量 Teacher 信号混在同一梯度中，无法判断
Teacher 可靠性是否决定下游表现。

### 1.2 可检验假设

若 Teacher 正确性是主要变量，则四条单源训练曲线应大致遵循：

```text
llava_hound > vsi_appr_order > vlm3r > spar_32view
```

若不同数据源都出现相同退化，则应优先怀疑数据源之外的共享机制，例如：

1. 全 response 等权 token 蒸馏改变了回答风格；
2. Teacher/Student thinking 状态不一致；
3. 固定 1,024 token 输出预算放大了长回答退化；
4. VOPD loss 与下游正确率之间缺乏直接约束。



## 二、实验设置



### 2.1 模型与蒸馏机制


| 项目                            | 实际设置                                         |
| ----------------------------- | -------------------------------------------- |
| 基座模型                          | Qwen3.5-4B                                   |
| 方法                            | MV-OPSD / VOPD token-level self-distillation |
| Student 输入                    | K 个普通视角                                      |
| Teacher 输入                    | 最多 8 个特权视角                                   |
| Student 视角 K                  | 从 `{2,3,4,5}` 逐样本随机抽取                        |
| Teacher 权重                    | Frozen，训练期间不更新                               |
| 蒸馏范围                          | Student 生成的全部有效 response token               |
| Prompt / image token          | 仅作为上下文，不计入 VOPD loss                         |
| Teacher thinking              | 开启                                           |
| Student / validation thinking | 关闭                                           |
| Logit 蒸馏                      | top-100 + tail bucket，广义 JSD                 |
| JSD 系数 α                      | 0.5                                          |
| Loss 聚合                       | `token-mean`                                 |


Teacher 不会生成另一条回答，而是将 Student 已生成的 response 拼接到 Teacher prompt 后，
对同一 response 做 teacher forcing。损失只覆盖 `response_mask=1` 的 token，
不覆盖问题文本、图像 token 或 chat-template 中的 thinking 标记。

需要注意：代码没有将 response 再拆成“推理段”和“最终答案段”。
因此，只要 Student 在 response 中生成逐帧分析、重复列表或 `<think>` 内容，
这些 token 都会参与蒸馏。

### 2.2 优化与采样超参数


| 超参数                 | 值             |
| ------------------- | ------------- |
| Learning rate       | `2e-6`        |
| Warmup              | 10 steps      |
| Weight decay        | 0.01          |
| Gradient clip       | 1.0           |
| Train batch size    | 64            |
| PPO mini-batch size | 64            |
| Micro-batch / GPU   | 1             |
| PPO epochs          | 1             |
| Rollout n           | 1             |
| 每步序列数               | 64            |
| 最大训练 response       | 1,024 tokens  |
| Teacher 最大 reprompt | 12,288 tokens |
| Student 最大 prompt   | 4,096 tokens  |


`adv_estimator=grpo` 仅用于跳过 Critic；在全部样本均有 Teacher 的情况下，
实际 actor loss 为纯 VOPD loss，不使用 reward advantage。

| Arm           | 节点     | 训练行数   | 计划步数 | 计划 epoch | 实际停止步数 | 实际数据进度 |

| `vlm3r`       | node-B | 30,567 | 477  | 1.0      | 116    | 24.3%  |


步数按 `floor(训练行数 / 64)` 设置，使每条 arm 原计划只过一遍数据，而不是统一套用 300 步。

实际视角分布：


| Arm           | Student 平均 K | Teacher 平均 N | Teacher 最大 N | `K < N` |
| ------------- | ------------ | ------------ | ------------ | ------- |
| `llava_hound` | 3.48         | 7.61         | 8            | 100%    |
| `vlm3r`       | 3.50         | 7.98         | 8            | 100%    |

| 项目        | 设置                              |
| --------- | ------------------------------- |
| Benchmark | VSI-Bench 全量                    |
| 样本数       | 5,130                           |
| 视频帧数      | 每场景 32 帧                        |
| 生成方式      | Greedy，`n=1`，thinking 关闭        |
| 最大输出      | 1,024 tokens                    |

## 三、实验结果



### 3.1 训练停止与产物状态

停止后，MV-OPSD 的 trainer、Ray 与 vLLM 相关进程均已退出。node-A 的 8 卡显存归零。
node-B 上仍有其他项目的 LLaVA/DeepSpeed 作业占用 GPU，该作业不属于本实验，未做干预。

### 3.2 VSI-Bench 主指标


| Arm           | Step 0 | Step 25 | 中间最低点      | 最后完整验证点     | 相对 Step 0     |
| ------------- | ------ | ------- | ---------- | ----------- | ------------- |
| `llava_hound` | 53.38% | 21.92%  | 20.55% @75 | 21.31% @175 | **-32.07 pp** |
| `vlm3r`       | 53.36% | 18.98%  | 18.81% @50 | 20.28% @100 | **-33.08 pp** |


两个数据源在第一次训练后评测（step 25）就已损失约 31–34 个百分点，

## 四、结果分析



### 4.1 直接失效机制：回答形态转为逐帧长推理

Step 0 的模型通常直接输出选项或数字，中位长度只有 4 token。训练后，输出开始反复使用：

```text
Frame 1-11 ...
Frame 12-13 ...
Let's look at Frame ...
```

在 `llava_hound` step 150 的验证输出中：

- 约 65.7% 的回答在前 500 字符就开始引用 `Frame` / `Image`；
- 平均每条输出引用 Frame/Image 约 34 次；
- 约 97% 输出达到生成上限；
- 约 52.5% 样本在被截断时，末尾没有可用的最终答案。

因此，低分主要不是解析器漏掉了正常短答，而是模型没有在预算内完成回答。

### 4.2 为什么 `answered/frac=100%` 仍然不能说明输出正常

训练后的长文中会出现大量帧号、数量、选项字母与中间判断。规则解析器往往能从中提取某个
“可评分字符串”，所以 `answered/frac` 接近 100%；但这个字符串未必是最终答案。

因此，在长回答退化场景下：

- `answered/frac` 只说明“文本里出现了可解析内容”；
- 不能说明模型完成了回答；
- 必须与 response median、截断率和末尾答案覆盖率联合判断。



### 4.3 为什么 VOPD loss 下降但能力下降

VOPD 优化的是 Student 与 Teacher 在 Student response 各 token 位置上的分布差异，
并不直接优化 VSI-Bench 正确率、答案完整性或输出简洁性。

本轮中：

- `llava_hound` VOPD loss：0.0670 → 约 0.009；
- `vlm3r` VOPD loss：0.1836 → 约 0.020；
- 同期 VSI-Bench 均由约 53% 降至约 20%。

这不是数值优化失败，而是**优化目标与任务目标错位（objective misalignment）**：
Student 更接近 Teacher 的条件分布，但这种接近主要体现在长篇分析风格，而非最终答案质量。

### 4.4 蒸馏代码范围核查

针对“是否错误蒸馏了 prompt + image + response”的疑问，代码检查结论是：

1. Teacher 与 Student 都会对完整的 prompt + image + response 做 forward；
2. 但 VOPD 只选择 response 对应的 logits；
3. `loss_mask = response_mask`，prompt 与 image token 不进入 loss；
4. Teacher 不自行采样，只在同一条 Student response 上做 teacher forcing；
5. response 内没有 thinking / answer 分段 mask，全部有效 token 等权参与蒸馏。

因此，**蒸馏范围实现与 Vision-OPD 相同，不是误把 prompt/image 算进 loss 的代码错误。**

### 4.5 Teacher thinking 不对称：最优先的机制假设

Vision-OPD 主实验中 Teacher 与 Student 都使用 non-thinking mode。本轮则设置：

```text
Teacher: enable_thinking=True
Student: enable_thinking=False
Validation: enable_thinking=False
```

Teacher prompt 停在开放的 `<think>` 上下文中，Teacher 用“推理态”分布为 Student 的
全部 response token提供 soft target；Student 自身却在“答案态”上下文中生成。

这不会让 prompt 中的 `<think>` token直接进入 loss，但会改变 Teacher 在每个 response
位置上的 next-token 分布，从而可能持续鼓励分析性、列表式、未收束文本。

该解释与以下现象一致：

- 两个独立数据源出现相同风格退化；
- 退化在 10–25 步内发生，早于一个 epoch；
- VOPD loss 快速下降；
- 输出大量逐帧枚举；
- 先前 non-thinking 的 v1 在 step 25 训练响应均值约 257、截断率约 0%，
本轮则分别达到 821/50% 与 1,024/100%。

但由于本轮同时改变了数据源、`rollout.n` 与 Teacher thinking，以上证据只能支持
“高度可疑”，不能构成单变量因果证明。

### 4.6 为什么单纯增大 max response 不是根治

本轮 1,024 token 的上限确实直接截断了大量最终答案，扩大上限可能暂时提高“答案能否写完”的比例。
但历史实验已观察到：将预算从 1,024 提高到 4,096 后，重复退化样本常常只是继续写更长，
VSI-Bench 并未恢复。

所以：

- 1,024 cap 是**结果恶化的放大器**；
- 长篇、重复、无法收束的生成策略才是更上游的问题；
- 只提高 cap 会显著增加计算成本，但不保证恢复能力。



## 五、结论



### 5.1 本轮得到的确定结论

1. **两条单源训练均失败，且失效发生在前 25 步。**
2. **VSI-Bench 下降不是评测链错误。** 两条 step 0 均正确复现基座。
3. **直接原因是响应长度失控与大规模截断。** 验证中位长度由 4 变为 1,024。
4. **VOPD loss 下降不能作为方法有效的证据。** 本轮再次验证了 loss 与下游能力可反向变化。
5. **数据源可靠性差异不是当前主要瓶颈。** 57.7% 与 44.0% Teacher 数据源都迅速坍缩。
6. **代码没有误蒸馏 prompt 或 image。** 但它对整段 response 等权蒸馏，不区分推理与最终答案。



### 5.2 尚不能下的结论

1. 不能断言 Teacher thinking 是唯一根因，因为没有 thinking on/off 单变量实验；
2. 不能据此判断 `llava_hound` 与 `vlm3r` 哪个数据集更适合训练；
3. 不能认为把输出上限提高到 4,096 就能修复；
4. 不能用 `answered/frac=100%` 证明模型仍在正常作答。



## 六、后续建议



### 6.1 最高优先级：最小因果验证

建议只做一条 25-step 诊断 arm：

```text
teacher_enable_thinking=False
其余保持当前 llava_hound 设置不变
```

验收点：

- step 10 / 15 / 20 / 25 的训练 `response_length/mean`；
- 训练 `clip_ratio`；
- step 25 全量 VSI-Bench；
- 验证 response median 与达到 cap 的比例；
- VOPD loss 平台。

若关闭 Teacher thinking 后长度不再爆炸，可确认本轮的 Teacher/Student mode mismatch
是主要机制；若仍爆炸，则应转向全-response token-mean 蒸馏和单源回答风格问题。

### 6.2 第二优先级：设计答案感知的蒸馏权重

如果研究目标是保留空间能力和最终答案格式，可以考虑：

- 对最终答案附近 token 提高权重；
- 对重复 Frame/Image 枚举降权；
- 增加 EOS / 长度正则；
- 或构造 answer-only mask。

这属于对 Vision-OPD 方法的扩展，而不是修复现有实现 bug。正式实现前应先定义：

1. 多选题、数值题与开放式描述题如何统一识别“答案段”；
2. 在线 rollout 中答案段识别失败时如何处理；
3. 是否会破坏 Vision-OPD 的 on-policy token-level 目标。



### 6.3 暂不建议

- 暂不启动 `vsi_appr_order` 与 `spar_32view`：共享失效机制尚未排除；
- 暂不继续当前 checkpoint：曲线在低平台稳定，额外训练不增加判别信息；
- 暂不只提高 response cap：它无法解决生成不收束问题。
